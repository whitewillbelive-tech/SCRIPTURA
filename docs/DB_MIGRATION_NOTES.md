# Database migration notes

Use PostgreSQL 15 or newer and a new, dedicated SCRIPTURA database, never an existing project database. The starter's `001_schema.sql` is unchanged. Apply `001_schema.sql`, then `002_append_only.sql` with `psql -X -v ON_ERROR_STOP=1 "$DATABASE_URL" -f ...`. The second migration adds triggers rejecting UPDATE, DELETE and TRUNCATE on review and provenance events, preserving existing rows. This is defense in depth: a database owner or superuser can disable triggers or alter schema; grant the application a restricted role and do not grant ownership or TRUNCATE. This mechanism does not prevent an administrator from changing history at the database level.

The starter requires application-level transactional checks for status promotions and source-locator verification. Its foreign keys and checks alone cannot establish a claim's evidence or attribution quality, nor protect raw content stored outside the database. Check rights at each storage, embedding, and redistribution operation. Audit target IDs are polymorphic and have no referential integrity; carefully validate target type and identity in application transactions. Address alignment is modeled with `passage_alignments` and claim-to-passage many-to-many links; references to works and schemes enforce matching corpora.

For rollback use `002_append_only.down.sql`, then `001_schema.down.sql` in a dedicated database. The 002 rollback refuses if either audit table has rows, and 001 refuses to remove any table if any of the 21 tables has rows; no data is deleted by the scripts. It removes the empty schema and should only be used on disposable or deliberately emptied databases. Reapply both migrations to restore. Reversing 002 removes the audit write protection, so stop all application writers first. Schema changes still require appropriate change control and backups in a future production rollout.

Run `psql -X -v ON_ERROR_STOP=1 "$DATABASE_URL" -f tests/database.sql` after migrations. Tests use a transaction and roll back synthetic fixtures. Running them on a nonempty or shared database is unsupported. Run forward/down/reapply in a fresh isolated test database to validate deployment; SQL file presence is not evidence of execution.

The starter does not impose a uniqueness constraint on `(from_passage_id, to_passage_id, alignment_type)` for passage alignments. Assess existing duplicates and alignment semantics before proposing an additive unique index; no automatic cleanup or destructive correction is performed here.
